## Purpose

为平台套餐订阅提供可配置、可验证且可恢复的支付能力，使生产环境能够通过微信支付 API v3 H5 收款，同时保持本地测试渠道和现有 Checkout API 的兼容性。

## ADDED Requirements

### Requirement: 支付渠道必须显式选择
系统 SHALL 根据环境配置为新订阅订单选择支付渠道，并 SHALL 在生产环境拒绝缺少必需凭据、未知渠道或默认 Mock 凭据；切换新订单渠道 MUST NOT 停止处理既有微信在途订单的通知和补偿。

#### Scenario: 生产环境启用微信支付
- **WHEN** 生产环境选择 `wechat` 且所有微信支付配置通过预检
- **THEN** 新订阅订单使用微信支付渠道创建

#### Scenario: 生产配置不完整
- **WHEN** 生产环境选择 `wechat` 但缺少商户身份、密钥、公钥或 HTTPS 通知地址
- **THEN** 系统拒绝进入可接单状态并报告具体的非敏感配置错误

#### Scenario: 已有微信订单不受渠道切换影响
- **WHEN** 默认新订单渠道从 `wechat` 切换为其他渠道
- **THEN** 系统仍接收并处理此前创建的微信订单通知和主动查单

### Requirement: 创建微信 H5 支付订单
系统 SHALL 使用微信支付 API v3 普通直连商户 H5 支付创建交易，金额 MUST 以整数分提交且与本地 CNY 订单精确一致，商户订单号 MUST 满足微信长度和字符约束。成功时现有订阅 Checkout API SHALL 通过 `checkout_url` 返回微信 `h5_url`。

#### Scenario: H5 下单成功
- **WHEN** 已鉴权租户为有效套餐创建订阅 Checkout 且微信接受交易
- **THEN** 系统保存微信 `h5_url`、支付过期时间和 `pending` 状态，并在 `checkout_url` 返回该链接

#### Scenario: 不确定的下单结果
- **WHEN** 微信请求在返回确定结果前超时或连接中断
- **THEN** 系统保持同一商户订单号并主动查单，不创建重复本地订单或新的微信交易

#### Scenario: 非法支付金额
- **WHEN** 订单不是 CNY、金额不为正或无法无损转换为整数分
- **THEN** 系统拒绝请求微信下单且不返回支付链接

### Requirement: 微信支付通知必须完成真实性与一致性校验
系统 MUST 使用原始请求体及 `Wechatpay-*` 请求头验证微信支付签名，MUST 使用 API v3 Key 对 `AEAD_AES_256_GCM` 资源执行认证解密，并 MUST 在业务处理前校验 AppID、商户号、商户订单号、交易类型、交易状态、币种和金额。

#### Scenario: 合法支付成功通知
- **WHEN** 通知签名和认证解密有效，且解密交易与本地微信订单完全一致
- **THEN** 系统接受通知并生成标准化的支付成功事件

#### Scenario: 通知正文被篡改
- **WHEN** 请求体与 `Wechatpay-Signature` 不匹配
- **THEN** 系统返回认证失败且不保存可处理事件、不改变订单或订阅状态

#### Scenario: 金额或商户身份不匹配
- **WHEN** 已验签通知中的金额、币种、AppID 或商户号与本地配置或订单不一致
- **THEN** 系统拒绝业务处理、记录脱敏安全告警且不激活订阅

#### Scenario: 微信签名探测流量
- **WHEN** `Wechatpay-Signature` 以 `WECHATPAY/SIGNTEST/` 开头
- **THEN** 系统将其作为失败签名拒绝且不执行降级或绕过验证

### Requirement: 支付通知必须可靠落库并幂等处理
系统 SHALL 在成功应答微信前持久化已验证通知，并 SHALL 使用渠道和通知 ID 保证事件唯一。业务状态变更 SHALL 异步执行，重复 HTTP 通知或重复队列投递 MUST NOT 重复激活订阅。

#### Scenario: 首次通知可靠接收
- **WHEN** 合法通知首次到达且事件成功持久化
- **THEN** 系统在 5 秒内返回空响应体 HTTP 204，并异步处理支付状态变更

#### Scenario: 数据库暂时不可用
- **WHEN** 合法通知无法可靠持久化
- **THEN** 系统返回 HTTP 5xx，使微信后续重试通知

#### Scenario: 重复通知
- **WHEN** 相同渠道、通知 ID 和载荷再次到达
- **THEN** 系统成功应答且只保留一个事件、只执行一次订阅激活

#### Scenario: 通知 ID 被不同载荷复用
- **WHEN** 相同渠道和通知 ID 携带不同的原始载荷
- **THEN** 系统拒绝新载荷并记录安全冲突，不覆盖首次事件

### Requirement: 支付成功必须原子更新订阅
系统 SHALL 在同一数据库事务内锁定支付事件、支付订单和订阅，将订单更新为已支付、保存微信交易号、激活对应套餐并更新租户当前套餐。已处理事件 SHALL 直接跳过。

#### Scenario: 订阅支付成功
- **WHEN** 已验证支付事件对应有效的待支付或创建中订单
- **THEN** 支付事件、支付订单、订阅和租户套餐全部提交为一致的成功状态

#### Scenario: 状态更新中途失败
- **WHEN** 任一订单、订阅或租户更新失败
- **THEN** 本次业务状态事务全部回滚，事件保留可重试失败状态且不会出现部分激活

### Requirement: 系统必须补偿漏单并关闭超时订单
系统 SHALL 定期扫描到期的微信 `creating` 或 `pending` 订单，并在改变本地终态前按商户订单号查询微信交易。已支付订单 SHALL 通过相同幂等处理链路补偿入账；确认未支付的到期订单 SHALL 在微信关单成功后取消。

#### Scenario: 查单发现已支付
- **WHEN** 到期订单未收到通知但微信查单返回 `SUCCESS`
- **THEN** 系统创建可幂等追踪的补偿事件并激活订阅

#### Scenario: 到期订单仍未支付
- **WHEN** 到期订单查单返回 `NOTPAY` 且微信关单成功
- **THEN** 系统将本地支付订单标记为取消且不激活订阅

#### Scenario: 查单暂时失败
- **WHEN** 微信查单因网络错误或可重试服务错误失败
- **THEN** 系统保留非终态并在后续调度周期重试，不推断支付失败

### Requirement: 支付密钥与日志必须满足生产安全要求
商户私钥和微信支付公钥 MUST 以只读 Secret 文件提供，API v3 Key MUST 通过 Secret 管理注入。系统 MUST NOT 在日志、异常响应或诊断输出中暴露私钥、公钥内容、API v3 Key 或完整通知密文。

#### Scenario: 记录微信 API 失败
- **WHEN** 微信 API 返回错误或支付通知校验失败
- **THEN** 日志仅包含请求标识、接口名、通知 ID、公钥 ID、订单号哈希、脱敏错误码、失败类别和耗时

#### Scenario: 密钥文件不可读
- **WHEN** 生产进程无法读取或解析配置的密钥文件
- **THEN** 配置预检失败且系统不接受新的真实支付订单
